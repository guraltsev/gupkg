## Design points

- The planner is a pure function, so the disk question is asked in `effects.find_unowned(system, desired, owners)` and the planner module owns the data and the refusal (`check_unowned`). `_prepare_install` (used by install, update, switch, repair and `--plan`) calls both right after `check_names`, before `_ask_about_other_versions`, before any download. `download_only` updates are not checked (they integrate nothing), like T14.
- No second scan: it uses the same `NameIndex` as T14 (`owners("")` = every package's names, this one included, so a package's own names are never unowned).
- Equality: shim `.exe` by bytes against the bundled launcher, `.config.toml` and wrapper by bytes of what would be written, shortcut by `ShortcutSpec` equality (target, arguments, working folder, icon, description, run_as_admin). An unreadable existing `.lnk` counts as different.
- The message names the paths the package would write (its own letter case; on disk it may be `Tool.exe`). The `--overwrite` value in the message is the union of the kinds already given and the kinds still needed, in the canonical order, so it is the one value that lifts the whole refusal.
- `check --fix` (`_repair`) calls the same check with no kinds and says "run `gupkg install <name> --overwrite=...` to replace it"; it changes nothing. It can only happen when the install record lacks an effect the manifest declares.
- The failure document has `code = file-exists` and, in the existing error mapping, `paths` and `overwrite` (like `name-conflict` carries `name` and `packages`). `list --json` and `info --json`: no code of them changed (`git diff main --stat` shows no viewdata, documents or results change); no new keys.
- Option: `install`, `update`, `switch`, `self repair`, `self update`. There is no top-level `repair` command (`install` of an installed package, `self repair` and `check --fix` repair).

### A real bug found by running the CLI through `gupkg.cmd`
`src\gupkg\gupkg.cmd` forwards arguments with a `shift` loop over `%~1`; a batch file splits arguments at `=` and `,`. So `--overwrite=orphaned-bin-files,orphaned-shortcuts` reached Python as `--overwrite orphaned-bin-files orphaned-shortcuts` and failed with "needs the kinds" (shown by running `src\gupkg.cmd --sandbox ... install tool --overwrite=orphaned-bin-files`: exit 2 although the flag was right; the in-process CLI tests passed). Fix in `cli._normalise`: the kind names that follow a bare `--overwrite` are its value again. Test: `test_the_value_split_at_equals_and_comma_by_gupkg_cmd_is_one_value_again`. Consequence: through `gupkg.cmd` an unknown kind or an empty item shows the bare-flag message (still exit 2 and the kinds listed), and `--overwrite orphaned-bin-files` (space) is accepted too.

## Inconsistencies found (AGENTS rule 13)
- `src\gupkg\gupkg.cmd` splits `--opt=a,b` at `=` and `,`: every `=` option reaches Python split. `--skip-checksum=cli` is hit the same way (the existing `_normalise` turns the bare `--skip-checksum` into `--skip-checksum=` and `cli` becomes a target). Not fixed (outside T16); only `--overwrite` is repaired in `_normalise`. Worth a task: forward arguments without the batch splitting, or document `--opt value`.
- `catalog.py` tells a package without an install record to run `gupkg install <name> --force`; `install` has no `--force` (from T14 log, still true).
- There is no top-level `repair` command although the engine, `self repair` and the docs speak of `repair`.
- The manager screen test for a refusal is a scripted double, so it cannot fail on main (same for T14's).

## Review round 1

**Blocking 1 (a file that appears between the plan and the write).** Executor order (read from `execute_install`): Resolve/copy-in, populate (fetch, verify, unpack, prepare), Activate (`current` moves), Integrate (effects written one by one), Finish (receipt and install record). Fix, one helper `executor._recheck_unowned` (same `find_unowned` and `check_unowned`; the package's own install-record names count as owned) used twice:
1. after populate and before Activate: a file that appeared and that `--overwrite` does not grant raises the same `FileExists` (exit 2). State at that point, said in the message: "<pkg> <version> was unpacked but not activated: `current`, the shims, shortcuts and the install record are unchanged." (the version folder stays; nothing else changed; the way out is the one in the message: move the file or give the flag.)
2. in `_integrate` right before each effect is written (`current` has already moved): a file that appeared since is not written over; the effect becomes an entry of the existing `integrate-failed` result (exit 3, T15's rule: the others are applied and recorded, the message says "<pkg> <version> is already active; this effect was not applied and is not in the install record", and the result already tells to run `gupkg check --fix` or install again). The flag grants such a file: it is replaced and the `replaced <path> (no installed package owned it)` line is printed (the line now also covers files granted late).
There is still a window of microseconds between the second look and the write of one file; closing it would need an exclusive create, which `write_bytes_atomic` and the shortcut writer do not offer (no lock added, as asked).
