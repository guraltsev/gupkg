## Item 2: which step fails and what state it leaves

The failing step is the **Finish** phase: `_write_receipt` fingerprints the files of the new `App` (`app_section(app_files(...))`) and cannot read
the locked file. By then: `current` already moved (Activate ok); Integrate ran (here skipped: nothing changed); the install record was
written (it comes before the receipt in Finish); only the receipt of the new version is missing. A failing Integrate step does not raise: an
effect failure is collected (`integrate-failed`, exit 3, with its own message), only the broadcast or an unexpected `OSError` could.

Rollback: **not added.** By the time Finish fails, the install record and the machine's integration (shims, shortcuts, PATH, env) already
describe the NEW version's effects. Moving `current` back would leave them pointing at effects of 1.1.0 while `current` is 1.0.0, so a correct
rollback would also have to restore the old install record and re-apply the old effects, which the code does not have at hand (it holds only the
old link, `run.view.installed.path`). That is not trivial or safe, so the message states the truth: the package is on the new version, the old one
is kept, `gupkg check <name>` shows the state and `gupkg switch <name> <old>` returns (verified: `switch hello 1.0.0` after the failed update gives
`ok hello 1.0.0: switched (was 1.1.0)`). `current` is never left missing: no path of this change touches `current`.

## Changes

- `engine/executor.py`: `_after_switch` context manager around the Integrate and Finish steps of `execute_install`: an `OSError` after
  `activated` is re-raised as `OSError` with the text `the <step> step failed: <error>. The package is now on <new>: `current` points to <new>; version
  <old> is kept. `gupkg check <name>` shows its state, `gupkg switch <name> <old>` returns to the old version.` (an install with no old version says only
  "`gupkg check <name>` shows its state"). Same exception type, so the exit code stays 3. `_purge_failure_text`: the failure of `remove_tree` in
  `--purge` becomes `<file> is in use by another program. The package is uninstalled: its integration and `current` are removed; its folder <folder> is
  still there. To finish, close the program, then run `gupkg uninstall <name> --purge` again.` (winerror 32/33; other errors: "could not be deleted
  (<reason>)" and "remove the cause"). Exit code stays 3.
- `engine/health.py`: problem `current-missing` (not fixable) when `current` is absent, the package folder has versions and the install record still
  lists effects. A plain uninstalled package (versions, no recorded effects) is still `not-installed`. `check` exits 3 `unhealthy`; `check --fix`
  does nothing for it (`repair` needs an installed package; `switch` refuses it too), so the text names `gupkg install <name>`.
- `engine/lifecycle.py` `_repair` (only `check --fix`): the planner's `App is missing and no way to recover it.` gets ` Reinstall with: `gupkg install <name>``.
  The exact `APP_MISSING_ERROR` text is unchanged for `pkg check` and the other uses.
- `selfmgmt/status.py`: `SelfStatus.current_problem`; `problems()` lists it, so `self status` is not `ok` (exit 3) and `--json` has the text in the existing
  `problems` list (no new key).
- Docs: `_docs/troubleshooting.md`, `tests/manual_smoke.md` 035-T13-3(b), 035-T13-8(c)(d).
