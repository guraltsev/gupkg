## 3. Old 1.1.1 installs

A 1.1.1 root has shims whose config targets `...\gupkg.cmd`. Hypothesis checked by reading the code, not by a full install:
`gupkg self repair` re-applies the effects of the *installed* version's own `pkg.toml`, which in 1.1.1 still says `.cmd`, so it cannot change them,
and `verify_each` compares the config on disk with the *record*, which matches, so no drift is reported either. What replaces them is an
update to the new release (`gupkg update gupkg`, or `U` in the manager): the desired shim effect differs from the recorded one,
`diff_effects` plans an `update`, and `_write_shim` writes the new config (with the fix above, also while the shim is running).
Test `test_an_update_replaces_the_cmd_shims_of_a_1_1_1_install_and_leaves_no_drift` covers this at effect level. The task's expectation
"drift reported and fixed by `gupkg self repair`" is NOT met and I did not make it so: reporting any `.cmd` shim target as drift would
also hit third-party shims, and repair would re-apply the same `.cmd` from the old manifest forever. The full update from a real
1.1.1 layout was not run (needs a release ZIP of the new version); manual check 035-T18-2 asks the owner to do it.

## 4. Open: the elevated launcher's step-3 check of a shim (NOT fixed, needs a decision)

`package-launcher.cmd` (PowerShell block, kind `s:`) takes the folder of the shim's `target` as "the gupkg tree" and treats its parent as the
version folder (`current` junction). With the new target `...\current\App\gupkg\python\python.exe` the tree becomes `...\App\gupkg\python`,
its parent `App\gupkg` is checked as a version folder, and the fourth level is the `current` junction checked as a plain object.
Demonstrated with the unchanged template (temp layout, scratchpad `chk.py`):

    GUPKG-ACL-FAIL <tmp>\root\gupkg\current: is a link

So an elevated package launcher that reaches step 3 (no bundled gupkg, no usable `gupkg-location`) with the new `gupkg.exe` on PATH refuses it
("Skipped PATH entry ... cannot be trusted in an elevated run"): fail closed, nothing weakened, but the new shim is not usable at step 3.
Steps 1-2 are unaffected (they use `gupkg.cmd`).

Ready fix (two lines in the PowerShell block, after `$tree = Split-Path -Parent $named`):

    if ($named -match '(?i)^(?<tree>.+)\\gupkg\\python\\python\.exe$') { $tree = $Matches['tree'] }

With it the check walks the whole App tree and accepts `current` as the version folder (verified with `chk.py`: no failure line). I reverted it:
changing the template changes every generated launcher, and `tests/test_registry_100.py::test_the_registry_rules_hold` then fails with
81 "differs from the launcher template" problems (launchers and fingerprints of `tests/fixtures/registry_100` must be regenerated). The task
forbids touching the registry. The patch and a test (a link planted in `App\gupkg` is found; `current` is not reported as a link) are
ready to apply together with a registry regeneration. Owner/controller decides.
