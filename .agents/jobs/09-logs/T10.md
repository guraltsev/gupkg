# T10 log: one typed reader; the manager reads in-process; failures are visible

Baseline (main deadc05, this worktree, before any change): 3534 passed, 11 skipped (6m57s).

## What was done
- `src/gupkg/report/documents.py` (new): frozen dataclasses (`ListRow`, `ListDocument`, `InfoRow`, `InfoDocument`, `RegistryRow`, `RegistryStatusDocument`,
  `PlanData`, `PlanItem`, `PlanDocument`, `ResultEntry`, `ResultsDocument`) and `read_list`, `read_info`, `read_registry_status`, `read_plan`, `read_results`.
  Each checks `api == 2`, raises `DocumentError` naming the field (`packages[1].version: expected text or null, got int`), and an `ok: false` document with no rows
  raises with the CLI's message (a failed call is never an empty list). Missing `mode` is now an error (the T06/T09 leftover).
- Writer and reader share the types for `list`, `list --names`, `info`, `registry status`: `viewdata.list_row/info_row/list_document/info_document/registry_status` build
  them, `ListDocument/InfoDocument/RegistryStatusDocument.to_data()` write them, `cli.py` calls these. `test_the_recorded_list_and_info_documents_are_rebuilt_...`
  proves `read(doc).to_data() == doc` for the recorded `list`, `info`, `registry status`.
  Not done for plan/result entries: their writers are `InstallPlan.to_data` / `PackageResult.to_data` in `gupkg.model.plan`, which cannot import `gupkg.report`; the
  reader types for them are covered by the recorded documents instead.
- `gupkg_ui/plans.py`: no field parsing left (`PackageRow` extends `ListRow`; `read_plan` maps `PlanItem` to `PlannedTarget`). `read_packages`, `read_info`,
  `read_checksum`, `PackageInfo` and `unreadable-plan` are gone. Behaviour change: a plan document the reader refuses (for example a bad `sha256` marker) now fails
  the whole plan with a message naming the field (flows turn it into "the plan could not be made" for every target; nothing runs) instead of failing one target.
- `gupkg_ui/reads.py` (new) `Reads(scope, system)`: `inventory`, `info`, `registry` call the same core functions as the CLI, in a worker thread.
  `UiEnvironment.source` returns them (field `reads` replaces them in tests). `gupkg_manager/batch.load_inventory`, the browser, `PackageScreen` and
  `ManagerApp.read_registry` use them; no read starts a subprocess. Operations still use `Client`.
- Visible failures: any exception of a read shows `ERROR: package list unreadable: ...` / `ERROR: registry unreadable: ...` in the status line (before the counts), the full
  text (`OSError: ...`) in a red notification and in `ManagerApp.problems`. `ManagerApp.read_registry` no longer swallows anything. The package view shows `Error: ...`.
  Deviation: the manager has no run log for reads, so "the run log shows the full text" is the notification plus `app.problems` (open question 1).
- `shorten_path` keeps `\\server\share` as the head of a UNC path. The run view puts its state before the scope (`status_line(own, own_first=True)`).
- Browser table: column widths are now set from the cells. With in-process reads (fast) the DataTable stayed at header width (`alph`, `outdat`) in about half of the runs
  (Textual measures columns on an idle event; the rows arrived before it). Found by the existing frame test failing at random; fixed, 6/6 green after.
- `tests/ui_support.py`: `FakeGupkg` picks the response by the full argument list (`list` and `list --available` differ), then `cmd:plan`, then the command word; the
  reads of the manager (`list`, `list --available`, `info`, `registry status`) are served in-process by `FakeGupkg.reads()` (`FakeReads`, through the real typed reader)
  and logged in `read_calls()`. `fixture_json(name, root, folder)` reads `ui` or `cli_docs`.
- `tests/fixtures/cli_docs/` (recorded by `record.py`, commands in its README) next to `tests/fixtures/ui/`: the ui set is the world of the screen tests with the events
  files of a real update; the cli_docs set is one document of every kind (registry, available with `system only`, failure, check). They answer different questions
  and both are recorded by a script, so I kept both and said why in the README.
